# Spec Delta

## Purpose

Gives mate a built-in, static database of which models are available on each supported backend, with the metadata and pricing needed to let a user pick one without already knowing an exact model id.

## ADDED Requirements

### Requirement: Catalog covers every supported backend
The system SHALL ship a model catalog containing entries for every `BackendKind` mate supports (`Huggingface`, `Gemini`). Each entry SHALL carry: a model id usable directly as `Config.model`, a human-readable display name, and per-million-token input/output pricing where the source data provides it.

#### Scenario: Listing models for a backend
- **WHEN** the catalog is queried for a specific backend
- **THEN** it returns only the entries belonging to that backend, each with a usable model id and display name

#### Scenario: Model id matches what the backend expects
- **WHEN** a catalog entry's model id is passed as `Config.model` to that entry's backend
- **THEN** the backend accepts it as a valid model identifier, with no reformatting required

### Requirement: Catalog is static and requires no network access to build
The model catalog data SHALL be vendored into the repository and regenerated by an explicit, committed script, not fetched over the network during `cargo build`.

#### Scenario: Building offline
- **WHEN** `cargo build` runs with no network access available
- **THEN** the build succeeds and produces a binary containing the full model catalog

#### Scenario: Regenerating the catalog
- **WHEN** a maintainer runs the catalog regeneration script
- **THEN** it fetches current data from the upstream source and overwrites the vendored catalog asset, without requiring hand-editing of the generated file

### Requirement: Catalog pricing is usable for cost tracking
When a catalog entry has pricing data, selecting that model SHALL make its input/output per-million pricing available to mate's existing cost-tracking path, without requiring a matching hand-written entry in `[pricing]`.

#### Scenario: Selecting a catalog model with known pricing
- **WHEN** a user selects a model that has pricing data in the catalog
- **THEN** mate's cost tracking uses that pricing for the session, with no `[pricing]` config entry required for that model
