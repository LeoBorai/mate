# Proposal

## Why

`mate` today hard-requires the `API_TOKEN` env var before the TUI even starts (`tui.rs:26`, `plain.rs:89`): with it unset, the process exits before rendering anything. There is also no built-in model catalog — `Config.model` is a free-text string and pricing is a 2-entry hardcoded table. A first-time user has to already know a valid `API_TOKEN`, a `BackendKind`, and an exact model id before they can see the UI at all. Tools like OpenCode and Pi instead let the user reach the UI first and pick provider/model/token interactively.

## What Changes

- Add a static, build-time-generated model catalog covering the `Huggingface` and `Gemini` backends, sourced from `anomalyco/models.dev`'s per-provider TOML files (`providers/huggingface/models/**/*.toml`, `providers/google/models/**/*.toml`, cross-referenced with `models/<org>/<model>.toml` for shared metadata), regenerated by a committed script rather than fetched at `cargo build` time.
- Add an in-TUI onboarding modal chain, shown automatically at startup only when `API_TOKEN` is absent: pick backend (Huggingface/Gemini) → pick a model from the catalog (filtered by backend) → enter a token → verify it against the provider → proceed to spawn sessions as today.
- **BREAKING**: `mate` (TUI mode) no longer exits immediately when `API_TOKEN` is unset. Startup behavior for the case where the token *is* set is unchanged.
- The entered token lives only in process memory for that run. It is never written to any config file, the catalog, or disk, and is never persisted for the next launch — the existing invariant that `API_TOKEN` never flows through the config chain (`config.rs:1-6`) is preserved, not loosened.
- `--plain`/`--print` is unaffected: it keeps failing fast with today's error when `API_TOKEN` is unset, since it has no interactive surface to onboard through.
- Onboarding is a startup-only gate, not a persistent feature: no new slash command is added to change provider/model/token mid-session. Switching later still goes through the existing flags/env var/config file plus a restart.

## Capabilities

### New Capabilities
- `model-catalog`: a static, in-binary database of (backend, model) entries — id, display name, context limits, and per-million input/output pricing — generated from vendored models.dev data by a repo script, with no network access at `cargo build` time.
- `interactive-onboarding`: the TUI startup behavior that, when `API_TOKEN` is absent, renders the UI immediately and walks the user through a backend → model → token modal chain (using `model-catalog`) before verifying the token and spawning sessions, instead of failing before the UI ever renders.

### Modified Capabilities
(none — no existing specs in this project)

## Impact

- `crates/mate-cli/src/tui.rs`: the current `api_token().ok_or_else(...)` hard-fail at the top of `run` moves behind the new gate; backend build + `verify()` + session spawn (currently eager) become conditional on onboarding completing.
- `crates/mate-cli/src/config.rs`: `api_token()` stays env-only; a new in-memory-only token path is added for the value entered through onboarding (still never touching figment/config).
- `crates/mate-tui/src/app.rs` (+ `ui.rs`): new onboarding modal state and rendering, following the existing `SpawnForm`/`DetailModal` pattern; `App` gains a "backend not yet built" state.
- `crates/mate-cli/src/plain.rs`: untouched.
- New build-time asset (generated catalog) + a new script/xtask to regenerate it from `anomalyco/models.dev`; `crates/mate-core` or `mate-cli` gains the catalog data type and lookup.
- No change to `Backend::huggingface`/`Backend::gemini`/`Backend::verify` signatures in `mate-core/src/backend.rs` — onboarding calls them with a token sourced differently, not a token sourced from a changed API.
